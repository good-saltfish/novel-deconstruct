# 0003 · 持续流 Kanban 与混合 PR 纪律

- 状态：Accepted
- 日期：2026-09-22

## 上下文

本项目维护者当前只有一人，每周可投入时间约 4–6 小时且不固定：

- 固定 sprint 的计划/验收/retro 仪式对单人、低时长项目开销过大，容易为凑节奏制造假进度；
- 但完全无流程又会回到"想一个做一个"、上下文丢失、Issue 与提交无法对应的状态；
- 严格"一切变更走 PR"对文档/typo 是纯摩擦，而功能变更直推 main 又会失去自查与 CI 门禁记录。

## 决策

- 采用**持续流（Kanban）**：Backlog → Doing → Review → Done 四列拉动，WIP 上限 1；
  远程仓库未启用前以根目录 KANBAN.md 为看板真源，启用后迁移到 GitHub Projects 并保持编号一致。
- **混合 PR 纪律**：功能、bugfix、架构调整必须走 feature 分支 + PR（CI + DoD 自查清单）；
  文档、注释、typo、配置微调允许直推 main。
- 主干模型为 GitHub Flow：main 始终保持可发布；远程启用后对 main 设置分支保护与必需检查。
- 提交遵循 Conventional Commits；功能 PR 必须 `Closes #N` 关联 Issue。

## 后果

- 好处：仪式开销最小化，同时保留 Issue 驱动、CI 门禁与决策可追溯；
  远程看板与本地看板是同一套四列模型，迁移无概念损耗。
- 代价：单人 PR 实质上是自审，自查清单可能流于形式——缓解方式是把红线写成测试
  （takeaways 留空、quote 定位、枚举受控），让 CI 而非自觉兜底。
- 放弃的方案：固定周/双周 sprint（仪式重于产出）；所有变更强制 PR（小修摩擦过大）；
  全直推 main（功能变更失去检查点记录）。
